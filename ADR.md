## ADR 1: структура хранения HTTP-заголовков в http_parser

**Контекст:**
Нужно хранить распарсенные заголовки и иметь поиск по имени.
В запросе обычно 5-15 заголовков. Зависимости — только стандартная библиотека.

**Рассмотренные варианты:**

| вариант | поиск | память |
|---|---|---|
| `std::vector<Header>` | линейный | 0 оверхеда, всё подряд |
| `std::unordered_map` | хеш-таблица | оверхед на бакеты |

**Решение:** `std::vector<Header>` с линейным поиском.

**Почему:**
  - **0 оверхеда** Вектор — просто массив в памяти. unordered_map тащит
    массив бакетов, ноды в куче, хеш-функцию.
  - **оптимально для нашего размера** 5-15 элементов, линейный поиск —
    несколько сравнений коротких строк. Хеш-таблица на таком N медленнее:
    хеш вычислить + прыгнуть по указателю в бакет.
  - **обращений мало** В коде лукапится только `Content-Length`, кэшировать нечего.

**TODO:**
  - Если заголовков станет много (50+) или будет лукап одного заголовка
    много раз — переход на `unordered_map`.
  - Если понадобится поиск по многим заголовкам сразу (например, сортировка
    для логов или дебага) — можно будет отсортировать вектор один раз и искать
    бинарным поиском (`std::lower_bound`).

## ADR 2: класс CAPI с RAII для сокетов и epoll

**Контекст:**
main() стал слишком большим, всё в одном файле. Нужен ручной клинап
при ошибке. Потенциальные утечки данных

**Решение:** класс `capi::CAPI` с RAII в деструкторе + конструктор с throw.

**Почему так:**
  - Лучшее взаимодействие с проектом
  - Удобно задать enum class для значений внутри проекта
  - Фабрика `CAPI::create()` оборачивает в try/catch и возвращает
    `std::optional<CAPI>` — main не падает на исключениях.
  - Деструктор закрывает fd если они валидны (`!= -1`), защита от double close
    у move-источника.
  - Вся нагрузка внутри класса, main.cpp просто использует его.

## ADR 3: OpState + OpCode + last_error_ вместо return int

**Контекст:**
Свободные функции возвращали `int` (0/1/-1), caller не знал что именно
произошло. errno терялся между вызовами (любой syscall мог его перезаписать).

**Решение:** `enum class OpState { OK, WARN, ERROR, FATAL }` +
`enum class OpCode` + `struct OpError` хранится в `CAPI::last_error_`.

**Почему так:**
  - Скопировал стиль errno
  - Типизированные коды вместо магических int — компилятор проверяет switch.
  - OpState отделён от OpCode: категория серьёзности vs конкретная причина.
  - run() стопит только на FATAL, WARN/ERROR — логирует и продолжает.

## ADR 4: `readn()` (`try_recv()`) как метод CAPI вместо inline recv()

**Контекст:**
У recv несколько потенциальных ошибок, которые надо обрабатывать,
что приводит к дублированию кода в местах с recv

**Решение:** метод `CAPI::readn(fd, buf, size)` — единая точка обработки
errno → OpCode (RECV_EAGAIN / RECV_CONN_RESET), пишет в last_error_.

**Почему так:**
  - on_recv различает EAGAIN (return OK, ждём следующего события) и реальную
    ошибку (return WARN) через `last_error_.code == RECV_EAGAIN`.

## ADR 5: std::string header = substr(...) с копией, а не string_view

**Контекст:**
Нужно читать первую строку запроса (ранее пропускалась).
Ранее, из-за erase строки, string_view ломался и первая строка у header 
(ранее header_view) отображалась неверно (body было в начале header)

**Решение:**
`std::string header = message.substr(0, pos + 2)` — копия. Переход
на view отложен.

**Почему так:**
  - Исходное сообщение может редактироваться в процессе, что может сломать логику, 
    копия хедера гарантирует правильность обработки
  - `pos + 2` в `message.substr(...)`, т.к. `http_parser::parse_header(...)`
    только строки, после которых есть `"\r\n"`
